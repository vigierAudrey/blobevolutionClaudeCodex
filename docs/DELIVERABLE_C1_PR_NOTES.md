# Deliverable C1: Chat WS→HTTP Fallback + Unified Error Handling — PR Notes

**Date**: 2026-01-12
**Scope**: Chat messaging only (`apps/web/app/messages/[id]/page-websocket.tsx`)
**Goal**: Add WS timeout → HTTP fallback + unified error handling using Deliverable B helpers

---

## Summary

This PR adds:
1. **WS → HTTP fallback on CLIENT_TIMEOUT** — When WS ACK times out, automatically retry via HTTP POST /conversations/:id/messages
2. **Unified error handling** — All chat errors (WS, HTTP, socket-error) now use `normalizeAppError` + `getUserFacingMessage`
3. **RATE_LIMITED cooldown** — Uses `retryAfterSeconds` from normalized error (preserves existing UX)
4. **Unknown error code logging** — Mandatory telemetry for unexpected error codes

**Anti-regression guarantees**:
- ✅ 1 click = 1 WS attempt + max 1 HTTP attempt (no retry loops)
- ✅ RATE_LIMITED cooldown UI unchanged
- ✅ `appErr.source` used for telemetry only, never for UX decisions
- ✅ UI displays `userMsg.text` only, not raw error messages
- ✅ No changes to booking/matching/reporting (out of scope)

## Behavior Changes

### 1. WS Timeout → HTTP Fallback (NEW)

**Scenario**: User sends message, WS ACK times out after 5000ms

**Before**:
- Shows error: "Erreur: ACK timeout after 5000ms"
- Message not sent

**After**:
- WS timeout detected (code === 'CLIENT_TIMEOUT')
- Automatic HTTP fallback to POST /conversations/:id/messages
- If HTTP succeeds → message sent, input cleared, no error
- If HTTP fails → normalized error shown (e.g., "Accès refusé" for FORBIDDEN)

**Anti-regression**:
- ✅ Only CLIENT_TIMEOUT triggers fallback (not NOT_CONNECTED, not INTERNAL_ERROR)
- ✅ 1 WS + max 1 HTTP per send() call
- ✅ No infinite retry loops

---

### 2. Unified Error Messages

**Before**:
- Raw error messages from server (technical)
- Example: "Erreur: Access denied"

**After**:
- User-friendly messages via `getUserFacingMessage`
- Context-aware (domain: 'chat', action: 'send-message')

**Examples**:

| Error Code | Before | After |
|-----------|--------|-------|
| FORBIDDEN | "Erreur: Access denied" | "Vous n'avez pas l'autorisation d'envoyer des messages à ce contact." |
| UNAUTHORIZED | "Erreur: Unauthorized" | "Votre session a expiré. Veuillez vous reconnecter." |
| VALIDATION_ERROR | "Erreur: Invalid content" | "Le message ne peut pas être vide ou dépasse la longueur maximale." |
| CLIENT_TIMEOUT (no HTTP fallback success) | "Erreur: ACK timeout after 5000ms" | "Le message n'a pas pu être envoyé dans le délai imparti. Veuillez réessayer." |
| INTERNAL_ERROR | "Erreur: Server error" | "Une erreur est survenue sur le serveur. Veuillez réessayer dans un instant." |

---

### 3. RATE_LIMITED Cooldown (UNCHANGED UX)

**Before**:
- Cooldown countdown shown in button: "Attendre 30s"
- Error message: "Trop de messages envoyés. Réessayez dans 30s"

**After**:
- Same behavior, but message generated by `getUserFacingMessage`
- Uses `appErr.retryAfterSeconds` (from normalized error)
- User message: "Vous avez effectué trop de tentatives. Réessayez dans 30 secondes."

**Anti-regression**:
- ✅ Cooldown timer unchanged
- ✅ Button disabled during cooldown
- ✅ No duplicate RATE_LIMITED error display

---

### 4. Unknown Error Code Logging (NEW)

**Scenario**: Server returns an error code not in ERROR_CODES or client-only codes

**Behavior**:
- Logs to console: `[UNKNOWN_ERROR_CODE] { code, source, debug }`
- Displays generic user message: "Une erreur inattendue est survenue. Veuillez réessayer."
- No automatic retry

**Example log**:
```javascript
console.warn('[UNKNOWN_ERROR_CODE]', {
  code: 'NEW_SERVER_CODE',
  source: 'WS_CHANNEL',
  debug: { status: undefined, url: undefined, details: { ... } }
});
```

**Purpose**: Telemetry to detect when backend adds new error codes

## Garde-Fous (Non-Negotiable Rules)

### 1. appErr.source = telemetry only ✅

**Rule**: `appErr.source` is NEVER used for UX decisions.

**Code evidence**:
- Line 86: `source: appErr.source, // debug/telemetry only` (comment)
- Line 230: Same comment in send()
- Line 346: Same comment in sendProposal()
- Line 236: Fallback trigger uses `appErr.code === 'CLIENT_TIMEOUT'` (NOT source)

**Why**: `detectSource()` is heuristic and can be wrong. UX must depend on `code`/`kind`/`canRetry`/`actionHint` only.

---

### 2. CLIENT_TIMEOUT = only fallback trigger ✅

**Rule**: HTTP fallback ONLY triggered by `code === 'CLIENT_TIMEOUT'`.

**Code evidence**:
- Line 236: `if (appErr.code === 'CLIENT_TIMEOUT') { /* HTTP fallback */ }`
- Line 352: Same in sendProposal()
- NOT_CONNECTED, NO_SOCKET, CONNECT_ERROR → no fallback (user sees error)

**Why**: Prevents fallback loops. Only timeout (no ACK response) warrants retry.

---

### 3. Anti-dup: 1 WS + max 1 HTTP ✅

**Rule**: Each send() call makes 1 WS attempt + max 1 HTTP attempt (if CLIENT_TIMEOUT).

**Code evidence**:
- Line 214: `const result = await sendMessage(input.trim(), 'TEXT');` (1 WS)
- Line 236-243: `if (appErr.code === 'CLIENT_TIMEOUT') { await apiClient.sendMessage(...); }` (1 HTTP)
- Line 243: `return;` (exits after HTTP fallback)
- No loops, no retries

**Why**: Prevents duplicate messages, retry storms.

---

### 4. UI displays userMsg.text only ✅

**Rule**: UI shows `userMsg.text`, never `appErr.message` or raw error.

**Code evidence**:
- Line 103: `setError(userMsg.text);` (socket-error)
- Line 263: `setError(httpUserMsg.text);` (HTTP fallback fail)
- Line 278: `setError(userMsg.text);` (RATE_LIMITED)
- Line 288: `setError(userMsg.text);` (other WS errors)
- Line 315: `setError(userMsg.text);` (HTTP-only errors)

**Why**: `appErr.message` is technical/raw. `userMsg.text` is user-friendly and context-aware.

---

### 5. appErr.message + debug = logs only ✅

**Rule**: `appErr.message` and `appErr.debug` used for telemetry, never displayed.

**Code evidence**:
- Lines 84-88: `console.warn('[UNKNOWN_ERROR_CODE]', { code, source, debug });`
- Lines 228-232: Same in send()
- Lines 344-348: Same in sendProposal()
- No UI renders `appErr.message` or `appErr.debug`

**Why**: Raw messages are technical. Debug info contains implementation details.

---

### 6. Unknown codes → log + generic message ✅

**Rule**: Unknown error codes trigger mandatory log + generic user message.

**Code evidence**:
- Lines 82-89: Check if code unknown → console.warn → still show userMsg.text
- Lines 226-233: Same in send()
- Lines 342-349: Same in sendProposal()

**Why**: Telemetry detects new backend codes. User sees safe fallback message.

## Risks & Mitigations

### Risk 1: HTTP fallback on slow networks

**Scenario**: WS times out frequently on slow/unreliable networks → many HTTP fallbacks

**Mitigation**:
- HTTP fallback is safe (idempotent POST with deduplication on backend)
- User sees no difference (message sent successfully)
- Future: adjust WS timeout (currently 5000ms) if needed

### Risk 2: Unknown error codes

**Scenario**: Backend adds new error code → generic message shown

**Mitigation**:
- Mandatory `[UNKNOWN_ERROR_CODE]` logging for telemetry
- Generic message is safe (doesn't mislead user)
- Future: add new codes to Deliverable B helpers + redeploy frontend

### Risk 3: RATE_LIMITED cooldown race

**Scenario**: User spams send button during cooldown

**Mitigation**:
- Button disabled during cooldown (`disabled={!!rateLimitedUntil || !input.trim()}`)
- Input disabled during cooldown (`disabled={!!rateLimitedUntil}`)
- Early return in send() if cooldown active (line 210)
